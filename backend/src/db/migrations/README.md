# migrations/ — วิธีแก้ฐานข้อมูลโดยไม่ล้างข้อมูล

## กติกาข้อเดียวที่ต้องจำ

**แก้โครงฐานข้อมูลเมื่อไหร่ ต้องเขียนสองที่:**

1. `../schema.sql` — แก้ inline เหมือนเดิม (ใช้สร้างฐานใหม่: dev, E2E)
2. `NNN_ชื่อสั้นๆ.sql` ในโฟลเดอร์นี้ — เขียนเป็น `ALTER TABLE` (ใช้กับฐานที่มีข้อมูลจริงแล้ว)

ถ้าสองอันไม่ตรงกัน **เทสต์ `e2e/schema-drift.spec.ts` จะแดง** โดยบอกว่าคอลัมน์ไหนต่าง

## ตัวอย่าง: เพิ่มคอลัมน์ใหม่

```sql
-- 001_add_student_nickname.sql
ALTER TABLE students ADD COLUMN IF NOT EXISTS nickname_en VARCHAR(100);
```

แล้วเติมบรรทัดเดียวกันลงใน `schema.sql` ที่นิยามตาราง `students` ด้วย

```bash
npm.cmd run db:migrate
```

## คำสั่ง

| คำสั่ง | ใช้เมื่อไหร่ |
|---|---|
| `npm.cmd run db:setup` | ฐาน dev / E2E — **ล้างทุกอย่างแล้วสร้างใหม่** จาก `schema.sql` |
| `npm.cmd run db:migrate` | ฐานที่มีข้อมูลจริง — รันเฉพาะไฟล์ที่ฐานนั้นยังไม่เคยรัน |
| `npm.cmd run db:migrate -- --baseline` | ฐานเก่าที่ตรงกับ `schema.sql` อยู่แล้วแต่ไม่มีประวัติ — ประทับตราโดยไม่รันอะไร |

`db:setup` ประทับตรา migration ทุกตัวให้อัตโนมัติ เพราะฐานที่สร้างจาก `schema.sql`
มีทุกอย่างครบอยู่แล้ว

## ข้อควรระวัง

* **`000_baseline.sql` ห้ามแก้** — เป็นสำเนาของ `schema.sql` ณ 2026-08-17 ที่ตรึงไว้
  เป็นจุดตั้งต้น · ข้างในมี `DROP TABLE` เพราะมันคือสำเนา จึงต้องไม่ถูกรันซ้ำ
  (runner กันให้แล้ว 2 ชั้น: ประวัติใน `schema_migrations` และการปฏิเสธฐานที่มีตาราง
  แต่ไม่มีประวัติ)
* **ตั้งชื่อขึ้นต้นด้วยเลข 3 หลัก** — runner เรียงตามชื่อไฟล์ ไม่ใช่ตามวันที่แก้
* **แต่ละไฟล์รันใน transaction ของตัวเอง** — ล้มกลางทางจะ rollback เฉพาะไฟล์นั้น
  แล้วหยุดทันที ไม่รันไฟล์ถัดไป
* **`legacy_*.sql.txt` คือซากก่อนมีระบบนี้** — เนื้อในถูกยุบเข้า `schema.sql` ไปแล้ว
  เก็บไว้เป็นบันทึกเท่านั้น นามสกุลไม่ใช่ `.sql` เพื่อให้ runner มองไม่เห็น
